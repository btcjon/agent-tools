# Dest Hermes native Notion exposure probe (2026-09-25)

Result: an **in-process, read-only** test supports—but does not finish—the native-tool hiding design. The probe reports `partial_in_process`, never a cutover `pass`. No live Hermes config, gateway, or Notion page was deliberately changed; the existing OAuth client may refresh its token as part of a read.

`adapters/registration/remote_native_filter_probe.py` ran on verified host `vmi3528421` through the active guarded bundle Python. It copied the current Notion MCP config **in memory**, set `tools.include: []` only on that copy, and used the installed Hermes `_make_tool_filter` to count model-facing native registrations. For the 45 tools returned by the independently connected Notion MCP transport, the filter registered **zero**. The transport still listed all 45 operations and fetched a known page. Its 19,046-character markdown body hash `809ec2f35427611dabdb5e62b1856d72138f678932382abbca2bf65bb787d499` matched a separate direct read using the unfiltered config. No content or credentials were printed. The live config SHA256 remained `686683f5da136a0b71fa1dcd8a23f4f4e97a644647f012f6026e662620e0a0b3`; `runtime/current` still pointed at `31cd802e18e2-dc3bac9`.

This does **not** prove that a fresh Hermes model session receives zero native Notion schemas, that bridge read and unsupported operations both work under an actual disposable profile, or that task quality remains unchanged. It proves only the installed filter predicate and the bridge transport can coexist with `tools.include: []` in the same isolated process. Do not change production `tools.include` on this evidence. Next proof: create a disposable Hermes profile without copying or printing credentials, show its model-facing tool list, run the bridge read and an unsupported-operation route, then compare startup bytes and held-out task outcomes to the unfiltered profile. If a disposable profile cannot reuse OAuth safely, keep native tools exposed and mark that gate blocked.

A second isolated process ran `adapters/registration/remote_registry_filter_probe.py` against the installed Hermes MCP registry, again with only **in-memory** config copies. It set `tools.include: []` for native Notion and disabled generated prompt/resource helpers on the bridge. Hermes registered **zero** `mcp__notion__*` names and exactly five `mcp__jev_skill_advisor__*` names: `capability_describe`, `notion_fetch`, `skill_read`, `skill_report_outcome`, and `skill_suggest`. The probe deliberately reports `partial_in_process`: it did not run an agent turn or capture a provider request. Afterward, the live config SHA256 was still `686683f5da136a0b71fa1dcd8a23f4f4e97a644647f012f6026e662620e0a0b3` and `runtime/current` still pointed at `31cd802e18e2-dc3bac9`. This strengthens the registry check but does not relax the disposable-profile gate above.

An otherwise identical baseline process with native tools visible registered 45 Notion tools. Their compact JSON registry definitions measured **236,783 bytes**; the five bridge definitions measured **3,356 bytes** in both processes. The filtered process registered zero native Notion definitions. These are Hermes registry schema bytes, **not** provider-request bytes, actual prompt tokens, or measured latency. Hermes may apply additional tool selection before sending a model request. `hermes profile create --clone` omits MCP OAuth token state; `--clone-all` copies it. We did not clone live credentials or switch profiles merely to fill this evidence gap.

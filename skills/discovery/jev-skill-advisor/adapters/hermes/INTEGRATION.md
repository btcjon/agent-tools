# Hermes pre-model capability hint

The installed plugin can supply the selected skill id and the task at the right hook. `register()` binds `pre_llm_call` to `_pre_llm_call`. That hook receives `user_message` and `session_id`, runs `skill-search --select` once, and has `selected.skill_id` plus `selected.content` before it returns context. This is before the first model call. The read-only copy on dest (`/home/dev/.hermes/plugins/warehouse-skills/__init__.py`, 387 lines, `plugin.yaml` 1.1.0) does not call capability selection. Its `_TURN` cache stores the context for that session and text, so the hint has to be built on the first pass.

`capability_hint.pre_model_context` keeps that skill body and the miss string. It calls Jev only when the selected skill is Notion and the caller passes a manifest path. No manifest, a non-Notion skill, a timeout, or a bad manifest leaves the skill context unchanged. The hint is at most five `id: description` lines, with `authorizes-calls="false"`. Schemas stay out of the context. The advisory correlation is checked and then discarded. It is not a tool receipt.

A `notion-fetch` call needs a service receipt. `pre_model_context` calls `suggest` with `explicit_skills` set to the skill id already chosen, which skips catalog retrieval and the rank scan, then writes `capability_ids` and `capability_manifest_hash` from that decision. Do not add `--capability-manifest` to the plugin's `skill-search` command; that would run capability selection inside the full selector as well as here.

`live_pre_model_context` is the plugin entry. It returns that same skill context for a non-Notion skill, a missing or blank session, an unreadable host, or any resolution failure. For Notion, and only when `enabled` is true, it resolves `ReleaseStore(release_root).resolve_profile(host=socket.gethostname(), harness="hermes", session_id=...)`, requires `selected.snapshot_id` to equal the release manifest `snapshot_id`, and takes the manifest from `capability_manifest_path(release_id)`. That path is the immutable release copy. There is no source-file fallback. `SkillAdvisorService(profile)` supplies `runtime.evaluator` and the receipt database, and `pre_model_context` is called once with that pair. The wrapper does not log the task or skill body, does not select from the warehouse again, and does not execute Notion writes.

`plugin_patch` rewrites the success branch to call `live_pre_model_context` with `release_root=RELEASE_ROOT` and `enabled=CAPABILITY_ENABLED`. `RELEASE_ROOT` defaults to `/home/dev/.local/state/jev-skill-advisor/releases`. `CAPABILITY_ENABLED = False` keeps today's skill injection. Turning the flag on is a later deploy step, after the session pin and the five-tool MCP process share that release. `plugin_patch` only returns text. The service object is what reads the provider credential. This module does not.

When enabled by that patch, `CAPABILITY_EVENTS` points to a host-local JSONL file. The pre-model branch logs one allowlisted discovery event with IDs, receipt, status, reason, hash, latency, and context byte count; it never records the task, skill body, page ID, or schema. If the event cannot be recorded, the hook returns only the original skill body and exposes no capability hint or receipt. The MCP bridge separately records receipt-correlated invocation events when configured with `--capability-events`.

The same patch registers Hermes `post_tool_call`. On the running dest tree (`/home/dev/.hermes/hermes-agent-maintained`, gateway launched from that checkout) `VALID_HOOKS` includes `post_tool_call`, and `model_tools._emit_post_tool_call_hook` passes `tool_name` plus `session_id`. Registry MCP tools use `mcp__<server>__<tool>`. The agent executor suppresses the inner emit and sends one terminal `post_tool_call` with that same tool name and `agent.session_id`. The callback is fail-open and does not replace the tool result. `observe_post_tool_call` writes one invoke row with `route` `native` only for `mcp__notion__*` after a verified same-session hint. Bridge names, other tools, a missing hint, and a telemetry error write nothing. Arguments, page IDs, results, tokens, exception text, and schemas are not fields.

Register the bridge under the Hermes server name `jev-skill-advisor`. The installed Hermes name converter then exposes `mcp__jev_skill_advisor__notion_fetch`, distinct from native `mcp__notion__notion_fetch`; the receipt hint names the bridge explicitly. If that server name changes, update the hint and re-test before enabling the plugin.

## Native route experiment

The installed Hermes now has its own `tool_search`/`tool_describe`/`tool_call` bridge that defers MCP schemas. The raw 45-tool Notion registry is therefore not the model's startup schema cost. New Opus advice is to keep native Notion tools available behind that bridge, rather than hide operations the Jev bridge does not implement.

`live_pre_model_context` reads `JEV_HERMES_CAPABILITY_MODE` per process: unset/`bridge` preserves the current receipt-bound `notion_fetch` instruction, `off` keeps only the selected skill body, and `native` makes the hint name selected **read-only** `mcp__notion__*` tools. The `native` names are derived only from selected entries in the release-pinned manifest, using the maintained gateway's verified `mcp__<sanitized-server>__<sanitized-operation>` convention and rejecting names over 64 characters; malformed or colliding names yield no hint. Selected write cards are omitted from the native hint pending a separate approval-path proof. It does not expose full schemas or unselected tools. The service receipt stays internal for route-observation correlation; it is not injected as authority for native calls. Discovery and selected native invocation events carry `route_mode`, and the observer ignores unselected operations. The current live plugin/config are not changed by this local code. Use comparable fresh CLI sessions with `off` and `native` for a read-only A/B after deploying the reviewed adapter, and record provider usage, tool calls, and independently judged task results before promotion.
